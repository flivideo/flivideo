Video project write-ownership: one queue, one writer per file

FliTools already queues transcription one job at a time and knows each file by its content. Today an agent can skip it, and three tools write SRTs into the same folders. This page sets the rules: everything goes through the queue, and each file has one writer.

2Identity is the content sha256

The same bytes mean the same job. If two callers ask for the same file at once, they get the same job. If one asks again later, it gets the finished result. Nothing is transcribed twice.

FliStudio askstitle-lab-final.mp4
/prod askssame file, 2 s later
→
sha256 601353f8…one open job per content
→
one runboth get the result; a later ask = reused: "cache"

This exists today: there's a cache keyed by sha256 (architecture.md:131), one open pass-2 job per content (:164), and byte-identical copies in other projects join it through alsoFor (:189). Every transcript json records its source.sha256. b01's json says 601353f864e0…, which lets any machine check that an SRT belongs to its mp4 without transcribing again (rule 5).

3One owner per output path

Decide where a final's SRT lives. Wherever that is, only FliTools writes it, and everyone else reads it. Copying it somewhere else makes a second file that goes stale. b01 proves it: it was copied at 13:06 and was already the older pass-1 version.

A · FliTools' transcripts/ is the place

videos/title-lab/ title-lab-final.mp4 title-lab-final.srt ← no one writes here transcripts/ title-lab-final.srt ← Publish reads this title-lab-final.json .txt engines/…groq.* …crisper.*

For

  • No FliTools change. It already writes here (flitools/src/transcribe/location.ts:23).
  • A pass-2 upgrade replaces the best file where it is, so Publish gets CrisperWhisper without anyone doing anything.
  • The same layout as footage/transcripts/ everywhere else.
  • Engine copies stay out of sight, as the brief ruled.

Against

  • FliStudio change: captionsFor (publish.ts:85) and video-text.ts:162 also look in transcripts/.
  • The asset list doesn't show folders (assets.ts:109), so the SRT needs a line on the video's card.
  • In Finder the SRT isn't next to the video for a manual YouTube upload.
  • /prod step 4 changes, and so does Jan's habit.

For

  • No FliStudio change. captionsFor already looks here.
  • Jan's /prod and /captions already put it here (b17–b20).
  • You can see it in Finder next to the video.
  • FliTools can already do this: save_to (flitools/src/capabilities.ts:30), and it's carried through pass 2 (editQueue.ts:32).

Against

  • Every caller has to pass save_to for finals. One that forgets writes to transcripts/ and you're back to two places.
  • A .json and .txt land beside the mp4 too. Where engines/ goes is not checked.
  • A path /captions already writes. It would have to stop, or its script-aligned version is overwritten (or overwrites FliTools').
  • Finals become the one place FliTools' layout doesn't apply.

A. transcripts/ is where FliTools already writes. Pass 2 upgrades it in place. Making it the only place means one FliStudio reader changes and no writer changes. B leaves the old risk in place, because any caller that forgets save_to starts a second copy. With A, the 14 copies beside the mp4s go to -trash/ once Publish reads the new path. FliCut's <name>-cut.srt is a different file that FliCut alone owns, so it stays.

4Auto-transcribe: a new final starts a job

When a *-final.mp4 lands in videos/<name>/, a FliTools job is queued. Nobody has to remember to do it, and an agent never has to improvise.

  • Who triggers it. FliTools has no file watcher (none found in flitools/src). FliStudio already queues on footage import. For finals, two triggers are proposed. The producer queues the job when its render exits (/prod Stage 6 through fli.py). FliStudio also queues one when it sees a final with no transcript (the Publish view). Rule 2 means a double request costs nothing.
  • Only finished files. A sha taken halfway through a render names the wrong content. Queue the job when the render exits, or when the file size has stopped changing.
  • Backfill. This would catch up b11–b13 shorts (never transcribed) by itself.

5Distributed machines: who may create a missing SRT

Building on the brief's rule: the machine that holds the recording writes its transcript files. The server only computes.

  • Who may create it. Only the machine that holds the mp4, and only through FliTools. A machine that only has the git checkout (no mp4) never creates an SRT. It waits for the pull.
  • How others avoid repeating the work. The pass-2 server already dedupes by sha (rule 2). That covers compute. It doesn't cover two machines both writing and then hitting a git conflict. The sha check before running covers that: if the SRT's json matches your mp4, you're done.
  • Real case. b01's pass 2 ran on mac-mini-m2 (engine.worker in its json), so the M2 is already doing pass 2 for this project.
  • Gap. The brief leaves two holders writing the same transcript as "last writer wins" (transcription-as-a-service.md, Not covered). In git that becomes a merge conflict on the SRT.
