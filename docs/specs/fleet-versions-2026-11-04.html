Bring the Fli apps up to date on other people's machines — from FliStudio

Verdict: buildable, small, and the risky part is consent, not code. The M2 and Jan's machine are already visibly stale (M2: FliStudio 9 commits behind with 9 uncommitted files; Jan: FliHub 194 commits behind). FliStudio has no version or update verb today. 2 · Versions measured today (real data)

"Behind" = commits between that machine's sha and the M4's main, which equals GitHub origin/main (confirmed with git ls-remote for all six). The M2's own cached origin/main is stale, so it understates (it said 8 and 0 where the truth is 9 and 2).

3 · The flow

  1. Versions (read-only, always safe): for each machine × app run git rev-parse HEAD, branch, status --porcelain, and compare to GitHub's main (ls-remote from FliStudio's own machine — one answer for everyone).
  2. Dry run of "Bring to latest": shows exactly what would happen — commits to apply, files touched, whether package-lock.json changed (so npm install would run). Changes nothing.
  3. Consent (see §5), then apply per app: git fetch → git pull --ff-only → npm ci/install only if the lockfile changed. Never restart.
  4. Refuse, with the reason shown, on: uncommitted changes · not on main · history diverged · no network to the source. No stash, no reset, no force — ever.
  5. After: cell turns to update ready · restart pending; the owner restarts when ready (existing app.restart where it applies). FliStudio detects "pending" by comparing the sha at process start with the sha on disk.

4 · How to reach other machines

Recommendation: (a) for David's own machines (M2, Roamy), (c) for Jan and anyone off the tailnet, with (b) deferred. Wrap both in one fixed-command layer so FliStudio never sends a free-form shell line: the server owns the four commands (rev-parse, status, fetch/ff-only pull, conditional npm install). SSH is the transport, not the permission model.
