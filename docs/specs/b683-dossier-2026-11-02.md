## 1. Executive context

This conversation began as a Saturday video production plan and evolved into a design discussion about the software needed to make the FliVideo production pipeline work end to end.

The immediate objective is to produce and publish videos about applications and extensions being built. However, the existing production tools do not yet support the entire journey reliably.

1. **Storyline Pilot** — collecting knowledge, constructing stories, reviewing scripts through synthesized audio, and preparing narration.

### 2.1 Important distinctions

**FliCut is not FliEdit.**

FliCut is a sequential editor. It is valuable for removing bad takes, removing unwanted material and joining recordings, but it cannot assemble the finished multilayered videos now required.

FliEdit is intended to perform that assembly. It has been built but has not yet been proven through production of a real finished video.

**B-Roll Pilot is not a capture tool.**

It organizes and indexes visual assets. Those assets originate from tools such as FliHub, Snappy, animation systems and image-generation workflows.

**Storyline Pilot is not a video editor.**

It organizes textual knowledge and produces and refines the story. Its script may reference demonstrations and other media, but it does not assemble the video itself.

## 4. Storyline Pilot — purpose and architecture

Storyline Pilot is the textual knowledge and story-development application.

Its purpose is to collect the raw material required to write a video, transform that material into a coherent story and support refinement before narration.

The application already supports collecting multiple documents and creating story material, but the conversation identified several gaps.

### 4.1 Raw ingredients versus storytelling instructions

The user observed that Storyline Pilot can contain dozens of documents, creating visual and conceptual overload.

More importantly, not every document has the same role.

There are at least two distinct categories.

| Category | Examples | Typical scope |
|---|---|---|
| Story ingredients | Build conversations, notes, research, demonstrations, transcripts | Video or related videos |
| Story instructions | Storytelling framework, hooks, brand voice, narration style, marketing guidance | Global or brand |

The second category must not be treated as ordinary video-specific reference material.

A storytelling template may be global. Brand voice and style instructions may belong to a particular brand.

The user referred to earlier discussions involving marketing, hooks and story structure that had not apparently been integrated into the extension.

### 4.2 Visual separation

Storyline Pilot should display these reusable instructions separately from raw story ingredients.

The preferred design does not require a large new navigation section.

One possibility is to place them at the top of the existing asset collection, using subtle visual styling to distinguish them.

They should remain visible and editable.

Their difference is one of **role and scope**, not editability.

### 4.3 Documents have different strengths

An earlier part of the conversation established that documents have different contributions to story construction.

A broad research or planning document may be useful to several videos without being suitable as the direct basis of any single script.

A video-specific transcript, by contrast, may contribute directly to the narration.

The document model should eventually distinguish the value or role of different documents, rather than treating all sources as equivalent.

## 5. Storyline Pilot — provenance and refreshable synthesis

This was one of the more difficult architectural problems discussed.

### 5.1 The drift problem

The user frequently works inside Claude Code conversations that contain two overlapping activities:

- Directing the software build.
- Discussing the video being created about that build.

A Claude conversation can continue after its contents have been captured into Storyline Pilot.

At the time of capture, Storyline Pilot may synthesize a document from the conversation.

However, if the Claude session continues, that synthesis may become stale.

The resulting problem is **drift between the source conversation and the synthesized document**.

### 5.2 Separate source provenance from synthesis

The discussion established a useful conceptual separation:

**Source provenance** identifies the original Claude session.

**Synthesis** is the derived textual artifact created from that session at a particular point in time.

These should not be treated as the same object.

A synthesis can become outdated without its source provenance changing.

### 5.3 Refreshable synthesis

The desired behavior is that a synthesized document can be refreshed from its original conversation.

It may be synthesized immediately when first captured, but should remain refreshable if the source session changes.

There is no requirement for Storyline Pilot to perform intelligent comparison itself.

In fact, the user explicitly corrected that assumption.

Storyline Pilot does not contain its own LLM capability. Intelligent synthesis happens through Claude Code.

### 5.4 Deterministic freshness indicators

The preferred application-side behavior is lightweight:

1. Store provenance information identifying the Claude session.
2. Record enough source and synthesis timing information to detect likely staleness.
3. Display a small visual indication when the synthesis is out of date.
4. Provide a copyable command that instructs Claude Code to refresh the synthesis.
5. Tell the user which Claude session or conversation should receive the command.
6. Allow Claude Code to regenerate and return the synthesis to the correct Storyline Pilot record.

This is analogous to an existing Captain's Log interaction in which a user copies a command associated with an entry and pastes it into Claude Code.

### 5.5 Unresolved details

The following remain implementation questions:

- How reliably can source-session modification time be determined?
- Should freshness use timestamps, message counts, hashes or another mechanism?
- How should the application identify the exact destination record for a refreshed synthesis?
- Should Claude regenerate the entire synthesis or incorporate changes into the previous version?
- How should refreshes preserve deliberate human edits?

The user did not select a final implementation strategy.

The principle is established: **deterministic freshness detection in the application, intelligent refresh through Claude Code**.

## 6. Storyline Pilot — recorded demonstrations as story content

A separate requirement emerged from planning the Overlay Pilot demonstration.

A recorded demonstration can contain spoken words that are intended to appear in the finished video.

This creates a special kind of story source.

Ordinary source documents are synthesized into a narrative.

A demonstration transcript may instead need to be preserved substantially as spoken.

### 6.1 Demonstration recording

The planned flow is:

1. Record the demonstration in FliHub.
2. Identify the recording as B-roll or demonstration footage.
3. Make the video available to B-Roll Pilot.
4. Make the associated transcript available to Storyline Pilot.
5. Represent the transcript as a distinct story asset or card.
6. Integrate that spoken content into the script at the appropriate point.

### 6.2 Concatenation versus synthesis

The distinction is important.

Some story content is generated from raw knowledge through synthesis.

Other content has already been spoken and recorded.

The latter should generally be integrated by concatenation or deliberate insertion, not rewritten as though it were merely research material.

The narration surrounding the demonstration should flow naturally into and out of it.

The final script should not duplicate words that already exist in the recorded demonstration.

### 6.3 Production consequence

The story needs to represent both:

- Words the presenter must still record.
- Words that already exist inside recorded media.

This is essential for preparing an accurate teleprompter script and later assembling the video.

## 7. Storyline Pilot — Director's Review Mode

This became the highest-priority new feature for the immediate Monday work.

The user described an approach already started the previous day.

Storyline Pilot could generate an audio rendition of the current script using Kokoro.

The user wants to edit the script **from the director's chair**.

Instead of repeatedly reading the script silently or asking Claude to revise it, the user listens to the narration.

When something sounds wrong, the user directly edits the corresponding text.

The revised section is regenerated and immediately available for another listen.

### 7.3 Kokoro and word alignment

Kokoro generates speech but does not directly produce the SRT word-timing output required for synchronized highlighting.

The proposed solution is to process generated audio through the existing Crisper Whisper alignment/transcription capability in FliTools.

This would provide timing information that Storyline Pilot could use for word highlighting.

The alignment quality still needs testing.

### 7.4 Playback controls

The desired playback experience includes:

- Play and pause.
- Speed up and slow down.
- Keyboard shortcuts for playback-speed adjustment.
- Visible word-level progress through the script.
- Direct editing of the passage being reviewed.
- Replay of newly regenerated audio.

The exact shortcut mapping was not specified.

### 7.5 Section-level regeneration

The script audio is already divided into sections.

When the user changes one section, the system should not regenerate the entire script unnecessarily.

Only the affected section should require new Kokoro output and word alignment.

The application must then maintain coherent playback across the complete script.

### 7.6 Claude's role

Most changes at this stage are expected to be small human edits.

However, larger story or structural changes may still require a Claude Code conversation.

The desired system therefore supports both manual editing and agent-assisted rewriting.

### 7.7 Immediate acceptance goal

By the end of Monday, the user wants to be able to listen to both scripts, improve awkward passages and arrive at narration-ready text.

The purpose is to make Tuesday's recording session straightforward.

## 9. B-Roll Pilot — overall purpose

B-Roll Pilot is the visual counterpart to Storyline Pilot.

The user described the relationship directly:

Storyline Pilot captures textual knowledge from different sources.

B-Roll Pilot captures visual knowledge from different sources.

Both are initially lightweight catalogues rather than complete production systems.

### 9.1 Broad definition of B-roll

For this workflow, B-roll means any visual asset that might be included in a video.

It does not have to be selected for the final edit.

Examples discussed include:

- Video clips and screencasts.
- Demonstration recordings.
- Screenshots.
- Generated images.
- Animation clips.
- Static images.
- Stop-motion sequences.
- Reusable call-to-action visuals.
- Thumbnails from other video projects.
- Brand-specific reusable media.

This definition is deliberately broad.

An asset can exist in the project's visual collection without necessarily being selected for the finished video.

### 9.2 Stop-motion examples

Two distinct examples were discussed.

**Sequential screen captures:** A user takes repeated screenshots of a webpage, application or other changing interface. The screenshots may later be displayed in sequence.

**Generated visual sequences:** Mike's OpenRig video was referenced as an example of generated LEGO-like robot scenes. The individual images were static, but displaying them sequentially created a stop-motion effect.

These are different creation methods, but both produce visual assets that B-Roll Pilot may need to manage.

### 9.3 Asset scope and reuse

Assets may belong to different scopes.

| Scope | Example |
|---|---|
| Video | A screenshot recorded specifically for the Overlay Pilot video |
| Related videos | A visual reference useful to several videos in a series |
| Brand | A reusable logo animation or call-to-action clip |
| Global | Generic footage or imagery useful across brands |

An asset may physically live in one location while being referenced by multiple projects.

The system should not require copying the same file into every video.

### 9.4 Reference application

The user has previously built a more complete B-roll management application for Joy.

That application reportedly includes filtering, grouping and other organizational features.

It should be investigated as a reference when implementing or expanding B-Roll Pilot.

However, the current pilot is intentionally narrower.

## 11. B-Roll Pilot — automatic description and enrichment

A significant new requirement emerged after the initial B-Roll Pilot discussion.

Visual assets should not simply enter the catalogue as anonymous files.

They should become understandable and searchable.

### 11.1 Images

When an image is ingested, the system should be able to produce a description of its contents.

It may also generate tags or keywords.

The user should be able to override or supplement the generated description and tags.

### 11.2 Videos

Videos require richer treatment.

The system should be able to describe their content, potentially at the level of individual scenes or time ranges.

Possible sources of understanding include:

| Source | Contribution |
|---|---|
| Vision model | Describes visible content and scene changes |
| Video frame analysis | Identifies frames or segments for further processing |
| Associated transcript | Explains what was being shown or discussed |
| Human description | Supplies intentional context |
| Human tags | Adds useful classification or search terms |
| Existing provenance | Identifies origin, project and related context |

The user suggested that some analysis might be achievable with FFmpeg or deterministic techniques, while richer interpretation may require vision models.

The exact model and processing approach remain open.

### 11.3 Joy's nail-art example

Joy frequently produces beauty-related content.

The user described the desire for a video-editing system to automatically find relevant B-roll such as:

- A red nail being painted.
- A red nail-color chart.
- A Beauty and Joy logo animation.

These assets should be retrieved because their descriptions and tags match the subject matter.

The creator should not have to search manually for every relevant clip.

This is a future retrieval capability enabled by today's enrichment work.

### 11.4 Screencast transcripts

A screencast may contain spoken instructions describing what is visible.

For example, the presenter might explain how to navigate an application and click particular controls.

That transcript can be valuable as metadata even if the audio is not used in the finished video.

The system should preserve the association between the recording and its transcript.

It should be possible to use the transcript to discover relevant footage without requiring the spoken words to appear in the final edit.

### 11.5 Background processing

Automatic descriptions, frame analysis and tagging should happen asynchronously.

The user does not want asset ingestion to depend on completing all enrichment work synchronously.

A file can enter the catalogue, then become more fully described in the background.

### 11.6 Responsibility boundary

The conversation considered whether the capture tool should perform enrichment or whether B-Roll Pilot should handle it.

No final decision was made.

However, the user leaned toward allowing B-Roll Pilot to perform asynchronous enrichment, particularly because capture should remain fast.

This becomes relevant to Snappy's architecture.

## 14. Snappy — region-based capture

**The region is the central abstraction in Snappy.**

The user repeatedly emphasized that remembering and reusing screen coordinates is what makes the workflow valuable.

### 14.1 Named regions

A region defines an area of the screen to capture.

Regions should be configurable and named.

For example:

- Code editor.
- Claude conversation.
- Browser application.
- Video preview.
- Presentation area.

The user may have many saved region definitions, but only a manageable subset should be active at once.

Approximately 10–15 active regions was suggested as a practical human limit, not a hard architectural restriction.

### 14.2 Region scope

Regions may belong to different contexts.

A region might be useful only for a particular video project.

Another might be reusable across a brand or recording style.

For example, the user might consistently position VS Code in the same part of the screen and want the same capture framing across many videos.

The region model should eventually support those reusable presets.

### 14.3 Multiple applications and displays

Snappy must account for setups involving:

- Multiple application windows on one display.
- Multiple applications across several displays.
- Different predefined capture areas.
- Rapid switching between those areas.

The user specifically described workflows involving a Claude conversation, a web application and a video system.

### 14.4 Region cycling

The desired interaction is fast.

Hotkeys should allow the user to cycle through predefined regions, including forward and backward movement.

A separate shortcut should capture the currently selected region.

The user should not have to redraw a capture rectangle every time.

### 14.5 Visual framing

A desirable feature is a visible outline or wireframe showing the selected region.

This would help the user confirm what is in the shot before capture.

It requires an appropriate native overlay mechanism.

The overlay should not contaminate the resulting screenshot.

The exact macOS implementation remains to be researched.

## 15. Snappy — capture modes

Several distinct capture workflows were described.

### 15.1 Tab-by-tab capture

A user has a browser application containing several tabs.

The capture region remains fixed while the user switches tabs.

Each tab is captured using the same coordinates.

This produces a consistent sequence of screenshots.

### 15.2 Scrolling-page capture

A user captures one portion of a webpage, scrolls down, captures the next portion and repeats.

Again, the region stays consistent.

The captured sequence can later be used in a tutorial or presentation.

### 15.3 Timed capture

A user selects a region and requests periodic screenshots.

For example, capturing ten images over ten seconds of gameplay.

This produces a sparse sequence suitable for stop-motion-style presentation without recording full-motion video.

### 15.4 Countdown capture

The user also wants the option to capture after a short delay, such as three or five seconds.

This is useful occasionally but is not expected to be the primary interaction.

### 15.5 Future multi-region capture

A later capability could capture multiple regions as part of a coordinated sequence.

For example, one region displays code while another displays an AI conversation.

The tool might alternate or coordinate captures across those regions.

This is future scope, not a requirement for the first build.

## 16. Snappy — architecture and integration

### 16.1 Native application

The user suggested Rust as a possible implementation language.

The reasons include performance, low-level operating-system integration and the need for responsive region overlays and hotkeys.

However, Rust was not a final decision.

The conversation also considered Swift as a possible alternative.

A native macOS implementation needs investigation before the technology choice is locked.

### 16.2 Interface model

Several forms were considered:

- CLI.
- TUI.
- Background service.
- Another lightweight native interface.

No interface model was selected.

The user's priority is fast operation, configuration and keyboard-driven interaction rather than a large conventional application window.

### 16.3 Send, don't store

One of the clearest architectural preferences was that Snappy should have a **send space rather than its own save space**.

The intention is not to build another media library inside Snappy.

Instead, Snappy captures an image and sends it to a configured destination.

The first destination will be B-Roll Pilot, associated with a particular video project.

This keeps capture and organization separate.

### 16.4 Capture metadata

## 24. Important architectural boundaries

Several boundaries recur throughout the conversation and should be preserved.

**Capture versus organization:** Snappy and FliHub produce assets; B-Roll Pilot organizes them.

**Organization versus intelligence:** B-Roll Pilot may store and display metadata, while specialized processing or external AI performs enrichment.

**Source versus synthesis:** Claude sessions are provenance sources; Storyline Pilot syntheses are derived, refreshable artifacts.

**Knowledge versus recorded speech:** Some script material is synthesized; other material comes from already-recorded narration and must be preserved appropriately.

**Catalogue membership versus edit selection:** An asset can be available to a video without being selected for the final cut.

**Sequential editing versus layered assembly:** FliCut and FliEdit solve different problems.

**Current pilot versus future platform:** The user repeatedly described broader possibilities without authorizing their immediate implementation.

**Shared reference versus copied file:** An asset may be reused across projects without requiring duplicate physical storage.

These distinctions should guide implementation decisions.

## 27. Instructions for future work

The following instructions emerged repeatedly and should guide the next Claude Code handoff.

2. **Inspect existing code before making implementation assumptions.** This is particularly important for Joy's B-roll application, earlier screen capture tools, Storyline Pilot and FliEdit.

4. **Preserve provenance.** Sources should remain traceable and reusable without unnecessary copying.

6. **Use Claude Code for intelligent work that the applications cannot perform deterministically.** Do not assume every extension needs an embedded LLM.

7. **Treat real video production as validation.** The applications should prove themselves by producing actual videos, not merely passing isolated feature demonstrations.

8. **Preserve both product requirements and story material.** The conversation itself contains material for future videos about Storyline Pilot, B-Roll Pilot and Snappy.
